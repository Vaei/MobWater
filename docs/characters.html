Characters in it

Immersion, wading, swimming, splashing and the ripples left behind. One component, and a seam where your movement code goes.

Add Mob Water Interaction to a character. Every tick it asks where the surface is at the measure point, and everything else follows from the answer.

It spawns nothing

No effects, no sounds. A plugin cannot know what your splash looks like, so this says where and how hard, and the project decides what that means. Bind OnSplash to a Niagara spawn and you have splashes; bind nothing and you have a component that costs one query a tick.
EventFires withWhen
OnEnteredWaterlocation, downward speedcrossing in. The speed is what decides whether this was a step or a fall, and therefore how big the splash should be
OnExitedWaterlocation, speedcrossing out
OnSplashlocation, strengthanything worth a splash, including the crossings above
These are the character crossing the surface. The camera crossing it is a separate event with its own hook - see hooking the camera going under. In anything but a first person game the two happen at different moments and in different places, and a lens effect bound to a character's crossing goes off while the camera is still in the air.

Footfalls

Splash(Location, Strength) is meant to be called by whatever knows when a foot lands. An animation notify knows; this component would have to guess. It splashes and pushes the surface in one call.

The movement seam

MobWater has no idea what movement component your project uses - stock, a fork, something written from scratch - and guessing wrong would be worse than doing nothing. So the movement half is deliberately thin and virtual.

OverrideDefault does
ApplyWade(Immersion01)scales a stock UCharacterMovementComponent's walk speed, 0 dry and 1 at the swim line
ApplySwimming(bool)sets the stock movement mode

Both are BlueprintNativeEvent, so a Blueprint subclass can take them over without C++. Override, and call nothing in the parent - the defaults are for the stock component and nothing else.

The walk speed before any of this touched it is captured once, on the first wade, not every tick. Reading it back after the scale has been applied and calling that the original is how a character ends up permanently slower every time it steps in a puddle.

Ripples from the feet

With Make Ripples on, the component owns a disturbance component and drives it. It is not persistent, so a character standing still lets the water settle - which is what still water does, and what a permanently churning puddle underfoot does not.

Networking

Everything here reads GetWaterInfoAtLocation, which is a pure function of position and time. Given a synchronised clock, two machines get the same immersion depth for the same character position, so wade and swim transitions happen on the same frame on both.

The ripples the feet leave are not in that answer and cannot be. They live in a render target that a dedicated server does not have. See the field is never authoritative.

Exclusion

An exclusion volume with Blocks Submersion on marks a point as dry, and the query does not fold that in. A character that has to be dry inside a hull needs to ask UMobWaterSubsystem::GetExclusionAtLocation as well - see Exclusion.
